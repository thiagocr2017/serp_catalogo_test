# Customer Profile - Technical Plan

## Archivos esperados

- `lib/modules/sales/presentation/pages/customer_profile_page.dart`
- `lib/modules/sales/api/customer_api.dart`
- `lib/modules/sales/api/customer_profile_dtos.dart`
- `lib/modules/sales/data/data_sources/supabase_customer_data_source.dart`
- `test/modules/sales/presentation/customer_profile_page_test.dart`
- `test/modules/sales/api/customer_profile_summary_test.dart`

## Contratos publicos

El perfil debe consumir una API publica del modulo `sales`, por ejemplo:

- `getCustomerProfile(customerId)`
- `getCustomerCommercialSummary(customerId)`
- `getCustomerOpenIssues(customerId)`

No debe consultar internals de `payments`, `inventory` o `product`. Si necesita
datos de otros modulos, estos deben exponerse por contratos publicos o vistas/RPC
propias del modulo de ventas.

## Datos calculados

Los resumenes deben venir de vistas o RPCs para evitar calculos pesados en UI:

- ultima compra;
- productos frecuentes;
- documentos abiertos;
- saldo y cuenta por cobrar;
- devoluciones recientes;
- alertas basicas.

## UX/UI

- Agregar salida explicita desde el perfil hacia `/sales/customers` en el
  `AppBar` o encabezado. El usuario no debe depender del historial del
  navegador/router para volver a la lista.
- Ajustar la navegacion del menu lateral para que `Clientes` navegue a la ruta
  indice `/sales/customers` incluso cuando la ubicacion actual empiece por ese
  prefijo, como `/sales/customers/:id`. El estado visual puede seguir usando
  prefijo, pero el `onTap` no debe bloquear rutas detalle.
- Agregar una banda de decision antes del detalle con cuatro respuestas:
  `Estado`, `Credito`, `Contacto` y `Proxima accion`.
- Ordenar alertas por severidad: credito vencido, sobre limite de credito,
  cliente inactivo y documentos pendientes.
- Mantener documentos en `TabBar`, pero reemplazar el vacio generico por
  mensajes especificos de cada pestana.
- Agregar semantica accesible a editar, encabezado, alertas, tarjetas metricas,
  secciones y pestanas.
- Limitar chips visibles en encabezado y mover excedentes a una seccion
  `Categorias y rankings`.
- Usar skeletons para carga de perfil/resumen cuando se implemente la fase de
  percepcion de carga.

## Riesgos

- Mezclar reglas de pagos en ventas sin contrato claro.
- Mostrar ranking o categorias inteligentes de forma demasiado explicita.
- Hacer consultas pesadas al abrir la pantalla.
- Duplicar informacion fiscal en varios modulos.
- Tratar rutas detalle como si fueran la lista por compartir prefijo y dejar al
  usuario atrapado en el perfil.
