# Customer Profile - Requirements

## Proposito

Crear una pantalla de perfil/display del cliente que concentre informacion
comercial, fiscal, historica, financiera y operativa para mejorar la relacion
con el cliente sin convertir el formulario de edicion en un tablero saturado.

## Alcance objetivo

- Mostrar datos generales: nombre fiscal, nombre fantasia, estado, telefonos,
  correos, direccion y geografia.
- Mostrar contactos con rol, telefono, email si existe y cumpleanos.
- Mostrar preferencias: factura electronica/tiquete, tipo de cliente,
  condiciones de credito, categoria manual, categoria inteligente y envio.
- Mostrar resumen comercial: ultima compra, productos frecuentes, productos
  comprados recientemente, pedidos abiertos, cotizaciones activas, facturas,
  devoluciones y consignaciones.
- Mostrar resumen financiero: saldo, cuenta por cobrar, limite disponible,
  documentos vencidos y alertas basicas.
- Mostrar alertas: cliente inactivo, credito vencido, saldo sobre limite,
  documentos pendientes. **Diferidos** por decision 34: datos fiscales
  incompletos y email faltante para factura electronica.
- Mostrar datos fiscales: identificacion, tipo de identificacion (resuelto desde
  el catalogo), actividad economica y el indicador de factura electronica.
- Permitir navegar a documentos relacionados sin importar internals de otros
  modulos.
- Las pestanas Pedidos, Facturas, Devoluciones, Cotizaciones y Consignaciones
  cargan documentos reales del cliente por `customerId`; registros legados sin
  ID pueden usar coincidencia exacta de nombre como compatibilidad visible.
- La alerta Documentos pendientes es accionable y su desglose muestra cada
  pedido, cotizacion, devolucion o consignacion contado por el resumen SQL, con
  estado y ruta de apertura. Si falla la carga, explica el error en vez de
  mostrar una lista vacia.
- Cada factura relacionada conserva un acceso contextual a devolucion con la
  factura precargada; por ahora muestra que la operacion no esta disponible y
  permite volver al perfil sin mutar datos.
- Cada factura se puede abrir desde la pestana Facturas y desde su lista
  principal; el detalle muestra snapshot, cliente y lineas y conserva retorno.
- La pestana Cotizaciones lista todos los estados del cliente, incluidos
  borradores, y cada elemento muestra estado/total/numero con enlace al detalle.
- Desde cotizacion abierta por el perfil se puede volver al mismo perfil.
- Acciones de estado compatibles con el API (marcar enviada, aceptar, rechazar)
  estan disponibles desde el perfil cuando el estado lo permite y se actualiza
  el chip/listado tras persistir.

## Principios UX

- El primer vistazo debe responder: quien es, si puedo venderle, que le debo
  cuidar y como contactarlo.
- Usar tarjetas compactas de resumen, no una lista interminable de campos.
- Separar informacion editable de informacion calculada.
- Las alertas deben ser accionables y breves.
- Los historiales largos deben tener filtros y enlaces a pantallas de detalle.
- La banda inicial de decision debe responder `Estado`, `Credito`, `Contacto`
  y `Proxima accion` antes de mostrar detalle largo.
- Las alertas financieras tienen mayor severidad visual que pendientes
  operativos.
- El encabezado debe limitar chips visibles para conservar jerarquia del nombre;
  los excedentes pasan a una seccion de categorias/rankings.

## Layout propuesto

- Encabezado: nombre fantasia, nombre fiscal, estado, categoria, acciones.
- Banda de alertas: credito, documentos, datos incompletos.
- Columna izquierda: datos de contacto, fiscal, envio y condiciones.
- Area central: resumen comercial y financiero.
- Seccion inferior o tabs: documentos, productos, contactos, actividad.

## Escenarios

### Cliente con saldo vencido

Given el cliente tiene facturas vencidas o saldo pendiente  
When se abre el perfil  
Then se muestra alerta visible con monto y acceso al detalle.

### Cliente contado

Given el cliente es contado  
When se abre el perfil  
Then se indica que no puede facturar a credito.

### Banda de decision

Given el usuario abre el perfil,
When se renderiza el primer bloque,
Then debe ver estado del cliente, condicion de credito/disponible, contacto
principal y proxima accion disponible o futura sin leer el resto del perfil.

### Retorno a lista de clientes

Given que el usuario esta en el perfil de un cliente,
When quiere volver al catalogo/lista de clientes,
Then debe existir una flecha en el `leading` del `AppBar`, con tooltip
`Volver a clientes`, que navegue a `/sales/customers` y no compita con `Editar`.

Given que el usuario esta en una ruta de detalle o edicion de cliente
(`/sales/customers/:id` o `/sales/customers/:id/edit`),
When selecciona `Clientes` en el menu lateral,
Then la app debe navegar a `/sales/customers` aunque el modulo de Clientes ya
aparezca seleccionado visualmente.

### Orden de alertas

Given existen varias alertas al mismo tiempo,
When se abre el perfil,
Then se muestran primero credito vencido y sobre limite, luego cliente inactivo
y finalmente documentos pendientes.

### Productos frecuentes

Given existen compras historicas  
When se abre el perfil  
Then se muestran productos frecuentes y fecha de ultima compra.

### Pestanas de documentos vacias

Given una pestana de documentos no tiene registros,
When el usuario la abre,
Then debe mostrar un estado vacio especifico para el tipo: pedidos, facturas,
pagos, devoluciones, cotizaciones o consignaciones.

### Documentos reales del cliente

Given existen documentos asociados por `customerId` y documentos historicos
asociados por nombre exacto
When se abre la pestana de ese tipo
Then se listan ambos sin duplicarlos, se muestra estado/numero/moneda/monto y
las acciones compatibles abren el documento con retorno al perfil.

### Alerta de documentos pendientes

Given el RPC cuenta documentos pendientes
When se pulsa la alerta
Then se abre el desglose por documento/tipo/estado y cada fila navega a su
detalle o lista pertinente; los registros visibles coinciden con el criterio
de estados del RPC.

### Accesibilidad

Given que el usuario navega con teclado o tecnologias asistivas,
When enfoca editar, alertas, metricas, pestanas o secciones,
Then cada bloque interactivo o informativo importante debe exponer nombre
accesible y proposito claro.

### Datos fiscales incompletos

**Diferido.** La decision 34 deja esta alerta fuera de la primera version.
Given el cliente requiere factura electronica y faltan datos fiscales/email  
When se abre el perfil  
Then se muestra alerta antes de crear documentos fiscales.

## Fuera de alcance inicial

- Motor completo de CRM.
- Envio automatico de emails.
- Calculo definitivo de ranking inteligente si no se define la formula.
- Pantalla final de logistica/envios.

## Decisiones cerradas el 2026-10-03

Ver `0.open-questions.md` seccion B.

- **Documentos en pestanas, no en orden unico** (decision 35): una pestana por
  tipo, con su lista propia — Pedidos, Facturas, Pagos, Devoluciones,
  Cotizaciones y Consignaciones. No hay un orden de prioridad entre tipos.
- **Alertas criticas de la primera version** (decision 34): credito vencido,
  sobre limite de credito, cliente inactivo y documentos pendientes. Quedan
  fuera, por ahora, datos fisculos incompletos y email fiscal faltante.
  La de **documentos pendientes** cubre pedidos sin despachar, cotizaciones sin
  respuesta, devoluciones sin procesar y consignaciones sin liquidar, y debe
  verse **menos urgente** que las de credito por ser la unica no financiera.
- **"Productos que le gustan"** (decision 36): significa **productos
  frecuentes**, los que mas compra por cantidad o frecuencia, calculado del
  historial. No ultimos comprados, ni favoritos manuales, ni sugerencias.
- **Rankings** (decisiones 31, 32, 33, 43, 44): etiquetas `Mayor Facturacion`,
  `Compra Recurrente` y `Mayor Valor Historico`, calculadas al cierre mensual,
  con la formula oculta siempre. Ver `../customer-management/4.customer-rankings.spec.md`.
