# Formulario de devolucion: plan tecnico

## Dependencias previas

- Implementar contratos/migraciones y pgTAP de
  `.specs/modules/sales/returns/`.
- Implementar `stock_role` y filtro de disponibilidad de
  `.specs/modules/inventory/returns/`.
- Implementar capacidad reembolsable/credito de
  `.specs/modules/payments/returns/`.
- Exponer API publica de preview/confirm de Sales; no importar internals de
  otros modulos. Cumplir `module-security-contract.md`.

## Presentacion

- La pantalla consume API publica de Sales y DTOs publicos de Product,
  Configuration, Inventory y Payments segun ownership; no calcula valores
  oficiales a partir de estado local.
- El servidor suministra snapshot de factura, restantes, saldo, monto elegible
  y errores tipados. UI deriva solo previsualizaciones informativas y refresca
  al cambiar lineas/resolucion.
- Un comando con UUID cubre toda la confirmacion; doble submit deshabilitado y
  reintento conserva el mismo ID/payload.
- Inventario y finanzas solo se consideran exitosos al recibir confirmacion
  atomica. No optimistic UI de stock/refund/credit.
- Usar tema/tokens e intenciones compartidas, lista de composicion y contexto
  de retorno segun arquitectura UX.

## Riesgos

- Una preview queda obsoleta: servidor recalcula y puede rechazar al confirmar.
- Precision/moneda: usar valores decimales y redondeo contractual, nunca double.
- Rutas desde cliente/factura deben volver al documento de origen.
- No exponer condicion de producto en salidas imprimibles al cliente.
