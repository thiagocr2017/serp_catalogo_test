# Customer Data Model - Requirements

## Proposito

Definir la evolucion del modelo de cliente sin mezclarla con documentos,
logistica o pagos.

## Campos objetivo

### Cliente

- `legal_name`: nombre fiscal/documental.
- `display_name`: nombre fantasia interno para busqueda y uso cotidiano.
- `identification_type_id`: tipo de identificacion.
- `identification_number`: numero de identificacion.
- `customer_type`: `CASH` o `CREDIT`.
- `credit_days`: dias de credito, requerido si `customer_type = CREDIT`.
- `credit_limit`: limite de credito. Para cliente de credito, `0` significa
  sin limite. Para cliente contado, el credito esta bloqueado por
  `customer_type`, no por el valor del limite.
- `requires_e_invoice`: true para factura electronica.
- `document_preference`: factura electronica o tiquete como preferencia/
  recordatorio, no como bloqueo absoluto.
- `country_code`: pais.
- `province_code` o `province_name`.
- `city_id` o `city_name`.
- `address`: direccion exacta libre.
- `preferred_carrier_id`: transporte preferido del cliente, tomado del catalogo
  global de transportes.
- `shipping_payment_policy`: politica habitual de envio del cliente: no paga,
  paga antes, paga contra entrega, incluido, por cobrar u otra configurada.
- `registered_at`: fecha de registro del cliente.
- `deactivated_at` y `deactivation_reason`.
- `manual_category_id`.
- `manual_category_ids`: varias categorias manuales si se modela relacion
  many-to-many.
- `smart_category`: calculada, no editable.

### Contactos

- `name`
- `phone`
- `role`
- `birthday`
- `email` opcional si el contacto recibe comunicaciones.

### Emails de documentacion

Se recomienda tabla separada `customer_emails`:

- `id`
- `customer_id`
- `email`
- `label`
- `purpose`: facturacion, documentos, comercial, otro.
- `is_primary`
- `is_active`

Motivo de la recomendacion: una tabla separada permite varios destinatarios,
clasificar usos y activar/desactivar correos sin meter listas separadas por
comas en `customers.email`. La consecuencia es que las consultas y formularios
son un poco mas complejos, pero despues sera mucho mas facil enviar facturas,
copias de documentos y comunicaciones comerciales sin duplicar datos en cada
contacto.

Decision: los correos de documentacion/facturacion pertenecen al cliente. Un
contacto puede tener su propio email personal, pero no debe ser la fuente
principal para enviar documentos. La razon es que la factura, tiquete, pedido,
devolucion o estado de cuenta se envia a la empresa/cliente y no siempre a una
persona fija; si una persona cambia de puesto o se elimina como contacto, los
destinatarios documentales no deberian perderse. La consecuencia es una tabla
adicional y una UI un poco mas completa, pero el envio automatico de documentos
queda mucho mas limpio.

## Reglas

- Email debe validarse por formato al crear y editar.
- Un cliente puede no tener email principal si no requiere factura electronica.
- Si requiere factura electronica, debe existir al menos un email valido para
  envio fiscal o mostrarse alerta/recordatorio mientras la app no emita factura
  electronica directamente.
- Nombre fantasia no debe aparecer en documentos fiscales salvo que se decida lo
  contrario.
- Desactivar cliente exige motivo.
- Cliente contado no permite facturas a credito.
- Un cliente contado puede recibir autorizacion puntual mediante PIN de un solo
  uso generado por usuario autorizado. Este flujo pertenece a un futuro modulo
  de autorizacion.
- Cliente de credito requiere dias de credito y limite de credito.
- Cuando vence el plazo de credito, el cliente queda moroso.
- Si saldo activo + nueva factura alcanza el limite, el documento se guarda
  pendiente de PIN y no continua como factura final.

## Rankings comerciales

El perfil de cliente puede mostrar rankings calculados, sin revelar al usuario
final la formula exacta cuando eso no aporte valor operativo.

- Ranking por monto comprado: nombre propuesto `Top Valor`.
- Ranking por frecuencia de compra: nombre propuesto `Cliente Constante`.
- Ranking por valor historico/LTV: nombre propuesto `Valor de Relacion`.

Recomendacion: mantener los rankings como calculos separados. La razon es que
un cliente que compra mucho dinero no siempre compra seguido, y un cliente muy
frecuente no siempre es el mas rentable. Separarlos ayuda a tomar decisiones de
venta y seguimiento sin mezclar senales. La consecuencia es que el perfil tendra
mas de una etiqueta y se debe evitar saturar la pantalla.

## Migracion recomendada

Implementar por bloques:

1. email/fantasia/contactos/cumpleanos;
2. identificacion y documento fiscal;
3. credito/tipo de cliente;
4. geografia;
5. emails multiples;
6. categorias;
7. envio.
