# Customer Management - UX/UI Roadmap

## Proposito

Definir la hoja de ruta UX/UI del modulo de Clientes para que cada pantalla
tenga un objetivo operativo claro, reduzca friccion y mantenga specs
verificables antes de implementar cambios visuales o de flujo.

Este documento dirige experiencia de usuario. No reemplaza los specs por
pantalla en `.specs/screens/customer-*`; cada cambio implementable debe quedar
reflejado en la carpeta de pantalla correspondiente:

- `.specs/screens/customer-list/`
- `.specs/screens/customer-form/`
- `.specs/screens/customer-profile/`

## Limite del cambio UX

La lista, el formulario y el perfil se gestionan como **un solo cambio/PR de
pantallas**. Incluye sus specs de pantalla, widgets, navegacion y pruebas de UI.
No incluye migraciones, RPC, reglas persistentes ni pgTAP. Esos contratos viven
en `6.customer-business-db.spec.md` y se entregan como cambio de negocio/DB
independiente. Las validaciones visuales del formulario presentan los errores
definidos por las RPC, pero no redefinen sus codigos ni reglas.

Esta division permite revisar la experiencia transversalmente y revisar el
contrato persistente junto con sus migraciones y pgTAP. La consecuencia es que
la UX puede depender del contrato de DB ya integrado; cambios coordinados deben
referenciar ambos cambios y respetar el contrato publicado.

## Ubicacion de specs UX/UI

La estrategia recomendada es:

1. Guardar la hoja de ruta transversal de Clientes en este archivo:
   `.specs/modules/sales/customer-management/5.ux-ui-roadmap.md`.
2. Registrar cambios especificos de pantalla en sus cuatro archivos existentes:
   `1.requirements.spec.md`, `2.technical-plan.md`, `3.tasks.md` y
   `4.tests.spec.md`.
3. Cuando una mejora sea puramente de auditoria UX, agregar una seccion
   `UX/UI` dentro del spec de pantalla, no una carpeta paralela.

Razon: Clientes combina busqueda, formulario, perfil, datos fiscales, credito y
envio. Un roadmap transversal evita decisiones contradictorias entre pantallas.
La consecuencia es que hay que mantener sincronizado este archivo con las specs
de cada pantalla cuando una tarea se mueve a implementacion.

Alternativa descartada: crear `.specs/ux-ui/`. Seria mas ordenado para diseno,
pero separaria la experiencia de las reglas de negocio y haria mas facil que el
agente de codigo ignore el contrato real de pantalla.

## Flujo objetivo de Clientes

El flujo principal debe ser:

1. El usuario entra a `Clientes` para encontrar o crear un cliente.
2. Desde la lista abre el perfil cuando necesita decidir si puede vender,
   contactar, revisar alertas o consultar historial.
3. Desde el perfil entra a editar si necesita corregir datos.
4. El formulario crea o edita datos maestros, pero no intenta responder todo el
   estado comercial del cliente.
5. Al guardar, el usuario vuelve al perfil del cliente para confirmar el estado
   completo y continuar operando.

Principio rector: la lista encuentra, el formulario captura, el perfil decide.

  para crear.
- `CustomerFormPage`: formulario full-page con datos del cliente, credito,
  documentos, ubicacion/envio, categorias y contactos.
- `CustomerProfilePage`: perfil con encabezado, alertas, contacto, fiscal,

## Principios UX/UI para Clientes

- La primera accion visible debe coincidir con el trabajo de la pantalla:
  buscar en lista, guardar en formulario, editar/operar en perfil.
- Los datos fiscales solo deben sentirse obligatorios cuando el flujo de
  factura electronica los hace necesarios.
- Las alertas del perfil deben diferenciar urgencia financiera de informacion
  operativa. Credito vencido y sobre limite pesan mas que documentos
  pendientes.
- La interfaz debe favorecer lectura rapida en desktop macOS: densidad media,
  texto escaneable, atajos visibles por convencion y foco por teclado.
- Los estados vacio, carga y error deben ser utiles, no solo informativos.
- El modo oscuro es el default; toda recomendacion visual debe usar
  `ColorScheme` y contraste AA.

## Roadmap por pantalla

### 1. Customer List - buscar y seleccionar

Objetivo del usuario: encontrar rapido el cliente correcto y abrir su perfil.

Problemas/fricciones actuales:

- El estado vacio general solo dice que no hay clientes, sin CTA contextual.
- El estado sin resultados no explica como ajustar filtros ni permite limpiar
  rapido.
- Los filtros actuales son utiles, pero no muestran conteo ni resumen de
  resultados.
- La lectura de cada cliente esta en cards simples; funciona, pero puede
  mejorar el escaneo con una estructura mas tabular en desktop.
- La auditoria marco falta de semantica accesible.

Mejoras recomendadas:

1. Convertir el header de lista en una barra operativa fija: busqueda, filtros,
   contador de resultados y accion `Nuevo cliente`.
   Razon: reduce desplazamiento y mantiene visible el control principal.
   Tradeoff: ocupa mas alto fijo en pantalla.
2. Agregar accion `Limpiar filtros` cuando busqueda o filtros reduzcan la lista.
   Razon: recupera al usuario de un filtro sin salida. Tradeoff: agrega una
   accion secundaria que debe mantenerse visualmente discreta.
3. Definir dos layouts: tabla densa para desktop amplio y cards compactas para
   ancho reducido.
   Razon: desktop favorece comparacion entre clientes; cards favorecen
   responsividad. Tradeoff: dos layouts exigen mas pruebas visuales.
4. Mejorar empty states:
   - Sin clientes: mensaje + CTA `Crear primer cliente`.
   - Sin resultados: mensaje + `Limpiar filtros`.
5. Agregar semantica para busqueda, filtros, crear cliente, estado y card/fila
   clicable.

Specs a actualizar antes de implementar:

- `.specs/screens/customer-list/1.requirements.spec.md`: estados vacios,
  contador y comportamiento de limpiar filtros.
- `.specs/screens/customer-list/2.technical-plan.md`: layout responsive
  tabla/cards y semantica accesible.
- `.specs/screens/customer-list/3.tasks.md`: tareas de header fijo, limpiar
  filtros, empty states, semantica.
- `.specs/screens/customer-list/4.tests.spec.md`: pruebas de empty state,
  limpiar filtros y navegacion por teclado/semantica cuando sea viable.

Criterios UX de listo:

- Buscar por texto y filtrar no oculta la forma de volver a todos.
- El usuario reconoce en una mirada nombre visible, razon social, tipo,
  estado, contacto primario y ubicacion/gira.
- La pantalla permite crear el primer cliente desde el estado vacio.
- La accion de abrir perfil es clara y accesible.

### 2. Customer Form - capturar sin saturar

Objetivo del usuario: crear o corregir datos de cliente con validacion clara y
sin perder cambios.

Problemas/fricciones actuales:

- El formulario contiene muchas secciones y campos; el usuario puede no saber
  cuanto le falta.
- La accion de factura electronica explica bien la regla, pero la dependencia
  entre documento habitual, datos fiscales y campos requeridos debe volverse
  mas escaneable.
- La validacion ya existe, pero al fallar se lleva al inicio; falta un resumen
  de errores navegable por seccion.
- Los contactos se editan como filas/cards completas; puede volverse pesado si
  hay varios.
- Las categorias comerciales aparecen como chips, pero no hay ayuda contextual
  sobre que son manuales y no rankings automaticos.

Mejoras recomendadas:

1. Agregar un indice lateral o superior de secciones con estado: `Completo`,
   `Requiere datos`, `Opcional`.
   Razon: reduce incertidumbre en formularios largos. Tradeoff: ocupa espacio y
   debe mantenerse sincronizado con validaciones.
2. Mantener todas las secciones visibles en desktop, pero permitir colapsar
   secciones opcionales como contactos y categorias.
   Razon: evita convertir el formulario en wizard y conserva velocidad para
   usuarios expertos. Tradeoff: requiere recordar estados abiertos/cerrados.
3. Agregar resumen superior de errores con enlaces/anclas a campo o seccion.
   Razon: cuando fallan varias reglas fiscales, el usuario entiende el conjunto
   sin buscar campo por campo. Tradeoff: duplica mensajes, por lo que debe ser
   breve y no reemplazar el error inline.
4. Separar visualmente campos que son fiscales condicionales:
   identificacion, tipo, actividad economica, direccion y correo principal.
   Razon: hace evidente por que aparecen errores cuando se elige factura
   electronica. Tradeoff: la seccion de datos principales queda menos lineal.
5. Para contactos, usar una fila resumida plegable despues de guardar/agregar.
   Razon: varios contactos dejan de alargar demasiado la pantalla. Tradeoff:
   editar un contacto requiere un clic adicional.
6. Agregar microcopy operativo para `0 = sin limite` y para politica de envio,
   manteniendo el texto breve.
   Razon: evita errores en datos con impacto comercial. Tradeoff: demasiada
   ayuda puede saturar; solo debe aparecer donde cambia una decision.

Specs a actualizar antes de implementar:

- `.specs/screens/customer-form/1.requirements.spec.md`: indice de secciones,
  resumen de errores, reglas de colapso y claridad de campos fiscales.
- `.specs/screens/customer-form/2.technical-plan.md`: estructura de secciones,
  estados por seccion y accesibilidad de foco/error.
- `.specs/screens/customer-form/3.tasks.md`: tareas de error summary,
  secciones colapsables, semantica, contactos compactos.
- `.specs/screens/customer-form/4.tests.spec.md`: submit invalido debe mostrar
  resumen + errores inline; foco/scroll al primer error; secciones opcionales
  no deben bloquear guardado.

Criterios UX de listo:

- El usuario sabe que datos faltan sin leer todo el formulario.
- Factura electronica explica y exige los datos correctos sin parecer una regla
  arbitraria.
- Cancelar, volver y menu lateral protegen cambios sin guardar.
- Crear, cargar, actualizar y desactivar siguen cubiertos por pruebas.

### 3. Customer Profile - decidir antes de operar

Objetivo del usuario: saber quien es el cliente, si puede venderle, como
contactarlo y que pendientes cuidar.

Problemas/fricciones actuales:

- El perfil no ofrece una salida visible a la lista de clientes; despues de
  crear un cliente y caer en su perfil, el usuario puede sentirse atrapado.
- El menu lateral puede dejar al usuario en el perfil actual cuando selecciona
  `Clientes`, porque la ruta detalle comparte el prefijo `/sales/customers`.
- El perfil ya tiene buen layout base, pero las metricas y alertas pueden
  competir por atencion.
- Las pestanas de documentos estan presentes, pero aun muestran vacios
  genericos.
- Las acciones se limitan a editar; falta direccion UX para acciones futuras:
  crear pedido, crear cotizacion, registrar pago o ver documentos.
- Las etiquetas de categoria/ranking pueden saturar el encabezado cuando haya
  varias.
- La auditoria marco falta de semantica accesible.

Mejoras recomendadas:

1. Agregar accion visible `Volver a clientes` en el encabezado del perfil.
   Razon: da una salida clara y no depende del historial de navegacion.
   Tradeoff: suma una accion secundaria al header, por lo que debe quedar menos
   prominente que `Editar`.
2. Corregir el menu lateral para que `Clientes` navegue a la lista incluso
   desde `/sales/customers/:id`.
   Razon: el menu debe funcionar como navegacion global, no como indicador
   pasivo del modulo activo. Tradeoff: hay que separar estado visual seleccionado
   de comportamiento `onTap`.
3. Definir una banda superior de decision con cuatro respuestas:
   `Estado`, `Credito`, `Contacto`, `Proxima accion`.
   Razon: el primer vistazo responde si se puede operar. Tradeoff: exige
   priorizar datos y no mostrar todo arriba.
4. Ordenar alertas por severidad:
   credito vencido/sobre limite, cliente inactivo, documentos pendientes.
   Razon: coincide con decision 34 y evita que lo operativo opaque lo
   financiero. Tradeoff: documentos pendientes se vera menos urgente aunque
   siga siendo importante.
5. Limitar chips visibles en encabezado y mover excedentes a una seccion
   `Categorias y rankings`.
   Razon: el nombre del cliente conserva jerarquia. Tradeoff: algunas etiquetas
   requieren bajar a la seccion.
6. Definir empty states por pestana de documentos:
   `Sin pedidos abiertos`, `Sin facturas`, `Sin pagos`, etc.
   Razon: el vacio genericamente repetido no ayuda a decidir. Tradeoff:
   requiere copy y pruebas por pestana.
7. Preparar espacio para acciones futuras sin implementarlas aun:
   `Nueva cotizacion`, `Nuevo pedido`, `Registrar pago`, `Ver cuenta`.
   Razon: orienta el perfil como punto de partida operativo. Tradeoff: no deben
   aparecer acciones sin contrato listo.
8. Usar skeletons para perfil y resumen comercial en lugar de spinner central.
   Razon: mejora percepcion de carga en pantallas de resumen. Tradeoff:
   requiere widgets de placeholder consistentes.

Specs a actualizar antes de implementar:

- `.specs/screens/customer-profile/1.requirements.spec.md`: banda de decision,
  severidad de alertas, limite de chips y empty states por pestana.
- `.specs/screens/customer-profile/2.technical-plan.md`: skeletons, semantica,
  retorno a lista, menu lateral, orden de alertas y placeholders de acciones
  futuras.
- `.specs/screens/customer-profile/3.tasks.md`: tareas de decision band,
  retorno a lista, menu lateral, empty states por documento, semantica,
  skeletons.
- `.specs/screens/customer-profile/4.tests.spec.md`: orden de alertas,
  ausencia/presencia de chips, empty states por pestana, navegacion a editar y
  retorno a la lista.

Criterios UX de listo:

- En menos de 5 segundos, un usuario puede responder si el cliente esta activo,
  si tiene riesgo de credito, como contactarlo y que accion sigue.
- Las alertas financieras son mas visibles que pendientes operativos.
- El perfil no muestra formulas de rankings.
- Cada pestana vacia comunica que falta y que accion futura corresponderia.

## Metricas UX recomendadas

- Tiempo para encontrar y abrir un cliente desde la lista: objetivo menor a
  10 segundos con busqueda.
- Tiempo para crear un cliente contado minimo: objetivo menor a 90 segundos.
- Tiempo para crear un cliente con factura electronica: objetivo menor a
  3 minutos con errores comprensibles.
- Errores de guardado por campos fiscales faltantes: deben bajar despues del
  resumen de errores.
- Porcentaje de usuarios que vuelven de perfil a formulario para corregir datos:
  sirve para detectar datos importantes mal ubicados o poco visibles.

## Reglas para agentes de implementacion

- No tocar UI sin actualizar primero el spec de la pantalla correspondiente.
- No mover reglas de negocio desde specs de `customer-management` a componentes
  visuales sin contrato publico o prueba.
- No mostrar formulas de rankings en ninguna pantalla.
- No convertir el perfil en formulario ni el formulario en perfil.
- No agregar acciones operativas futuras hasta que exista spec del flujo destino.
- Mantener todo texto visible en espanol.
- Usar APIs publicas de modulos; no importar internals de otros modulos.

## Proxima recomendacion

Empezar por `Customer List` y `Customer Profile` antes que por el formulario.
Razon: son mejoras de menor riesgo que aclaran el flujo completo y corrigen la
auditoria de accesibilidad. La consecuencia es que el formulario largo sigue con
friccion por una fase mas, pero se reduce primero el riesgo de navegacion y
comprension general del modulo.
