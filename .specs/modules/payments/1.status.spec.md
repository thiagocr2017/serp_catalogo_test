# Payments Status - Estado real frente al SDD

## Proposito

Registrar que partes del diseno de `.specs/modules/payments/sdd-historical.md` estan implementadas y
cules no, tras la decision del propietario de **alinear el SDD al codigo**
(2026-10-03). Sirve de referencia para `.specs/refactors/02-tech-debt-plan.md`.

Todo lo de este documento fue verificado contra `lib/modules/payments/`, las
migraciones y la base local el 2026-10-03.

## Resumen

`lib/modules/payments/` tiene 1122 lineas con estructura completa de modulo
(`api/`, `domain/`, `data/`, `presentation/`, `di/`, `payments_module.dart`),
esta cableado en `lib/main.dart`, y la base tiene tablas y RPC propias creadas
por `20260930020000_payments_module_foundations.sql` y
`20260930060000_payments_create_refund_rpc.sql`.

Las lecturas y las escrituras **funcionan**. Las escrituras usan el camino
correcto.

## Camino de escritura

`lib/modules/payments/data/data_sources/supabase_payment_data_source.dart`
realiza **8 llamadas RPC** y no escribe ninguna tabla por acceso directo. El
acceso directo a tablas solo se usa para lectura, que es lo que permite el
`GRANT SELECT`:

| Metodo de `PaymentApi` | RPC invocada | Estado |
|---|---|---|
| `getPayments` | `from('payments')` (lectura) | Funciona |
| `getPaymentById` | `from('payments')` (lectura) | Funciona |
| `getPaymentMethods` | `from('payment_methods')` (lectura) | Funciona |
| `getMoneyAccounts` | `from('money_accounts')` (lectura) | Funciona |
| `createPayment` | `create_payment` | Funciona |
| `confirmPayment` | `confirm_payment` | Funciona |
| `cancelPayment` | `cancel_payment` | Funciona |
| `createPaymentMethod` | `create_payment_method` | Funciona |
| `createMoneyAccount` | `create_money_account` | Funciona |
| `createExpense` | `create_expense` | Funciona |
| `transferBetweenAccounts` | `transfer_between_accounts` | Funciona |
| `createRefund` | `create_refund` | Funciona |

Es el patron que exige `.specs/architecture/module-security-contract.md` §6: las tablas de Pagos
conceden solo `SELECT` a `anon` y `authenticated`, y toda escritura pasa por
una RPC `SECURITY DEFINER`. Verificado con `set local role authenticated`
dentro de `rollback`:

```text
select (public.create_payment_method('Prueba RPC','t','d','i')).name;
 metodo_creado
---------------
 Prueba RPC

select (public.create_money_account('Caja prueba','CASH','USD','t','d','i')).name;
 cuenta_creada
--------------
 Caja prueba
```

## RPC disponibles en la base

11 funciones, todas `SECURITY DEFINER`. `audit_payments` no tiene `EXECUTE`
para clientes, que es el patron esperado para una funcion interna:

| RPC | Ejecutable por `anon`/`authenticated` |
|---|---|
| `create_payment(p_command_id, p_customer_name, p_total_amount, p_currency_code, p_exchange_rate, p_notes, p_components jsonb, p_actor_name, p_device_name, p_device_identifier)` -> `payments` | Si |
| `confirm_payment(p_payment_id, p_actor_name, p_device_name, p_device_identifier)` -> `payments` | Si |
| `cancel_payment(p_payment_id, p_reason, p_actor_name, p_device_name, p_device_identifier)` -> `payments` | Si |
| `create_payment_method(p_name, p_actor_name, p_device_name, p_device_identifier)` -> `payment_methods` | Si |
| `create_money_account(p_name, p_account_type, p_currency_code, p_actor_name, p_device_name, p_device_identifier)` -> `money_accounts` | Si |
| `create_expense(p_concept, p_beneficiary, p_amount, p_currency_code, p_money_account_id, p_expense_date, p_actor_name, p_device_name, p_device_identifier)` -> `expenses` | Si |
| `create_refund(p_payment_id, p_amount, p_currency_code, p_reason, p_actor_name, p_device_name, p_device_identifier)` -> `refunds` | Si |
| `transfer_between_accounts(p_from_account_id, p_to_account_id, p_amount, p_currency_code, p_exchange_rate, p_notes, p_actor_name, p_device_name, p_device_identifier)` -> `void` | Si |
| `dispatch_transfer(p_document_id, ...)` -> `void` | Si |
| `mark_transfer_in_transit(p_document_id, ...)` -> `void` | Si |
| `receive_transfer(p_document_id, ...)` -> `void` | Si |
| `audit_payments(...)` -> `uuid` | No (interna) |

Notas:

- `create_payment` recibe `p_command_id`, o sea que ya es idempotente por
  clave, conforme a `.specs/architecture/module-security-contract.md` §5. Las demas RPC **no**
  reciben clave de idempotencia; es deuda abierta si van a soportar reintentos
  o cola offline.
- `dispatch_transfer`, `mark_transfer_in_transit` y `receive_transfer` operan
  sobre `p_document_id` (documentos de inventario), no sobre cuentas
  monetarias. No confundirlos con `transfer_between_accounts`.

## Nota de correccion

Una version anterior de este documento afirmo, erroneamente, que las escrituras
no persistian porque la capa de datos accedia a tablas de solo `SELECT` sin
usar RPC. El diagnostico salio de un `grep 'rpc('` que no casa con la forma
real de invocacion, `_client.rpc<Map<String, dynamic>>(`. La afirmacion se
corrigio verificando las 8 llamadas RPC existentes y ejecutandolas contra la
base. Queda anotado para que no se repita: **una ausencia en un `grep` no prueba
una ausencia en el codigo**.
